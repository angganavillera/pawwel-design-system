Overview

Design Guidelines

This guide documents the PAWWEL design system in a cleaner, scrollable format for design handoff, collaboration, and implementation reference. It provides direct access to components, tokens, spacing, motion, and interaction rules without requiring deep inspection of Figma source files.

✨
Standards of Behavior
System consistency is maintained through a token-driven ecosystem. Semantic tokens define behavioral intent, while primitive values may still be used for foundational mapping when needed. The primary rule is to avoid hardcoded values to preserve flexibility, scalability, and accessibility across the experience.
Core Principle

Design Philosophy

PAWWEL is a companion app, not a pet tracker. Every design decision must reinforce the emotional connection between the user and their pet — mediated through the PAWWEL robot.

🧡
Emotional over Data
Show "Apple seems calm today" not "Anxiety score: 2.3". Interpret, don't report.
🍎
Apple-Level Polish
Use native iOS materials, physics-based animations, and system haptics. Never fight the platform.
🌿
Breathable Layout
Generous whitespace. Hierarchy through scale and weight, not borders and boxes.
😊
Robot as Character
PAWWEL is a companion, not a device. States, expressions, and animations must reflect personality.

Anti-patterns to avoid

✓ Do
  • Use named emotional states ("Calm & Happy", "Playful", "Needs Attention")
  • Prioritize narrative cards over data tables
  • Warm, organic color palette (brown/orange foundation)
  • Spring-based animations for natural feel
  • SF Pro for all primary interface typography
✗ Don't
  • Show raw sensor data or decimal scores
  • Use cold blues, purples, or enterprise palettes
  • Heavy borders everywhere (dashboard aesthetic)
  • Linear easing for UI transitions
  • Mixing other body fonts with SF Pro
Foundation

Token Architecture

The PAWWEL system is structured in layers to keep the experience visually consistent, scalable, and easy to maintain across the product.

1
Foundational Values
Core palette, spacing, typography, and radius values used as the visual foundation of the system.
2
Functional Intent
Semantic tokens that define interface intent such as primary text, secondary surfaces, active states, and emphasis.
3
Contextual Application
Component-level usage where tokens are applied consistently across buttons, cards, navigation, forms, and interaction states.
Rely on Intent
  • Use semantic tokens like fg.primary and bg.secondary for consistent UI behavior.
  • Primitive values are allowed for foundational mapping and system setup.
  • The main goal is maintaining consistency across components and screens.
  • Semantic structure helps the interface scale more cleanly as the product grows.
Avoid Fixed Values
  • Avoid hardcoded colors directly inside components whenever possible.
  • Prefer semantic tokens to keep the interface flexible and scalable.
  • Hardcoded values can create inconsistencies between screens and states.
  • Primitive tokens are still acceptable as foundational references when needed.

Usage Guidelines

DO
  • Use display and heading tokens for robot emotional state titles and section headers.
  • Use body and caption tokens for descriptive copy, helper text, and status descriptions.
  • Use Semibold (600) for interactive labels, quick action buttons, and pill text.
  • Scale type size contextually — larger for emotional moments, smaller for metadata.
DON'T
  • Mix heading and body token sizes within the same content hierarchy.
  • Use caption or label sizes for primary readable content — minimum body for paragraphs.
  • Apply display tokens inside cards or compact components.
  • Use raw font sizes — always reference the semantic typography tokens.

Design Rules

Do
  • Resolve every visual decision from type, size, isIcon, and isDisabled.
  • Use semantic tokens for surface, foreground, border, radius, spacing, and motion.
  • Scale icon-only dimensions and icon-label gap with the selected size.
  • Disabled removes interaction, not only visual prominence.
Do Not
  • Reach for hex values, ad-hoc padding, or local corner radius.
  • Invent button variants that don't exist in Figma.
  • Treat disabled as a type — it is a state that applies to every type and size.
  • Let icon-only buttons shrink below the platform touch target.

Interaction Behavior

State Visual response Motion
Rest Default tokens for the chosen type. None.
Pressed Subtle inward compression — feels physical, never theatrical. spring.snappy · ~3% scale reduction.
Focused 2pt outer ring in color.border.active, offset 2pt from the button edge. Fade in duration.fast.
Loading Label is replaced with an inline spinner; size and width are preserved. Cross-fade duration.fast.
Disabled Disabled tokens, ~72% opacity, no hit-testing. Instant.

Content Guidelines

  • Lead with a verb. Labels describe an action, not a destination — Give Treat, not Treat Page.
  • Keep labels to 1–3 words. Sentence case. No trailing punctuation.
  • One Primary per view. Multiple Primaries flatten hierarchy.
  • Destructive labels name the consequence — Delete Moment, never Confirm.
  • Icon-only buttons require a VoiceOver label that reads as a verb.
📐
Minimum touch target: 44pt
All interactive elements must meet iOS HIG 44×44pt minimum. Use .frame(minHeight: 44) even on small-looking elements. Do not rely on visual padding alone.

Buttons 2

Extended button variations for contextual interactions — toggle switches, radio buttons, FAB, date picker pills, and dropdown date pickers. These components support selection, scheduling, and utility-driven actions across the PAWWEL ecosystem.

Button Toggle

Toggle switches for binary on/off settings. Used for AI Autosuggest, feature flags, and preference settings. Supports label-only and label + description variants.

VariantUsage
Toggle onlyCompact settings rows without label
Toggle + labelSingle-line setting with name
Toggle + label + descriptionSetting that needs supporting context
Do
  • Use for settings that take immediate effect — no confirm step needed.
  • Label describes the active state: "AI Autosuggest" not "Enable AI Autosuggest".
  • Show description text only when the setting has non-obvious consequences.
Don't
  • Use toggles for actions that require a follow-up step — use a button instead.
  • Stack more than 6 toggles without a section divider.

Button Radio

Radio buttons for single-selection within a group. Supports leading and trailing icon positions, multiple sizes, and full pill-style variant for emphasized selections.

VariantUsage
Radio leadingStandard list selection (radio left of label)
Radio trailingiOS-native style (radio right of label)
Radio pill (filled)Emphasized selection in filter or onboarding contexts
Do

  • Pre-select the most common or recommended option by default.
  • Use pill variant when the radio group is the primary action on screen.
Don't
  • Mix leading and trailing variants in the same group.
  • Use radio buttons for multi-select — use checkboxes instead.

Accessibility

Required
  • Every input carries a descriptive accessibilityLabel matching its visible label.
  • Error messages announced by VoiceOver immediately on reveal.
  • Slider announces current value as accessibilityValue on change.
  • Phone flag picker button: accessibilityLabel: "Country code, [country name]".
Avoid
  • Validation that fires mid-keystroke before the user finishes typing.
  • Sliders without labeled min/max — VoiceOver users need context for the range.

Centered overlay dialogs for confirmations, warnings, and focused micro-interactions that require the user's full attention before continuing. Modals in PAWWEL are used sparingly — always for decisions with consequence.

  • Lead with the consequence in the title: "Delete moment?" not "Are you sure?".

Modals interrupt the flow deliberately. Use that interruption to create clarity, not anxiety. The warm backdrop and softly scaled entrance communicate that PAWWEL is asking, not demanding.

Usage Guidelines

Use breadcrumbs only when the navigation depth exceeds two levels and the user may need to jump up multiple levels at once. For simple one-level-back navigation, the standard iOS back button is sufficient. Breadcrumbs in PAWWEL appear at the top of a screen beneath the navigation bar, never inside a card.

Dos & Don'ts

Do
  • Truncate long breadcrumb items with an ellipsis and full text in a tooltip on tap.
  • Make each breadcrumb item tappable — it navigates to that level directly.
  • Show the current page as the last item, non-tappable and in color.fg.primary.
Don't
  • Show more than 4 levels — collapse ancestors into "…" if needed.
  • Use breadcrumbs on the root or home screen — they imply depth that doesn't exist there.
  • Replace the navigation bar back button with breadcrumbs — use both together.

Design Principles

Breadcrumbs in PAWWEL are quiet orientation aids — small, low-contrast, only seen when needed. They say "you're here, and here's how you got here" without shouting. They sit comfortably above the content and disappear when not relevant.

Expandable / collapsible content sections used in FAQ, robot feature explanations, feeding schedule details, and health insights. Accordions let users find the depth they need without overwhelming the default view.

Usage Guidelines

Use accordion when content is related but not all of it is needed on first view. Health insights ("Why is Apple anxious?"), robot feature explanations, and feeding schedule sub-options are good candidates. Limit to one level of nesting — never accordion inside accordion. Allow multiple items to be open simultaneously unless the content is mutually exclusive (e.g. FAQ only one at a time).

Dos & Don'ts

Do
  • Show a skeleton loader at the bottom of an infinite scroll list while the next page loads.
  • "Load more" button uses the btn-secondary btn-md style — never primary, it's not the main action.
  • Show "All caught up" when the end of an infinite feed is reached — with warmth.
  • Page dots are limited to 7 maximum; use a line indicator for longer flows.
Don't
  • Auto-load next pages without user scroll — don't jump the layout while the user is reading.
  • Show a numeric page count ("Page 3 of 47") in the iOS app — it breaks the companion feel.
  • Use infinite scroll for data that requires exact position reference (health logs, tables).

The Moments feed should feel endless and warm — like scrolling through a journal, not a database. Infinite scroll serves this. Health logs require precision — "Load more" gives the user control over how deep they go. Always match the pagination pattern to the emotional register of the screen.

Motion Principles

  • Motion has weight. The robot breathes, the cards settle, the sheets fall into place. Nothing snaps into existence.
  • Motion reinforces, never announces. If the user notices the animation more than the change, the motion is too loud.
  • Looped motion stays calm. Idle and breathing loops use long springs so the eye reads life, not activity.
  • One-shot motion has personality. Treat dispense, outfit changes, and celebrations are allowed to be playful — but always brief.
  • Reduce Motion is honored everywhere. All idle loops, transitions, and decorative motion collapse to an instant change when the system requests it.
